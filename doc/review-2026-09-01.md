## BLOCKER

**1. `pyproject.toml` — wheel/sdist build is completely broken.**
`pyproject.toml:5-12`'s `[project]` table has no `version` and no `dynamic = ["version"]`.
PEP 621 (enforced by `pyproject-metadata`, which meson-python uses) requires one or the
other. Reproduced directly: `pip install .` / `python -m build` / `pip wheel .` all fail
at metadata parsing, before meson even runs. `.github/workflows/ci.yml` never exercises
this path — all three CI jobs call `meson setup` directly, bypassing `pyproject.toml`
entirely — so this has never been caught. Fix: add `dynamic = ["version"]` to `[project]`;
root `meson.build:9` already declares `version : '0.1.0'`.

## HIGH

**2. `SoftwareBackend`: unsynchronized `std::unordered_map` shared across threads.**
`src/backends/software_backend.cpp` — `windows_` and `snapshots_`
(`include/prism/backends/software_backend.hpp:46,57`) are plain `std::unordered_map`,
no mutex. `drain_window_requests()` (`software_backend.cpp:54-74`, emplace at 63-64) and
`drain_close_requests()` (`:81-86`, erase at 83-84) mutate them on the SDL/main thread
(inside `run()`'s `SDL_EVENT_USER` handling). `submit()` (`:306-309`) calls
`snapshots_.find()` from the **logic thread** (`model_app.hpp`'s `publish_entry`, called
on every dirty-widget publish and every animation tick) with no synchronization at all.
Per the standard, a modifying container op (`emplace`/`erase`) concurrent with any other
op on the same container from a different thread is UB. `window_requests_`/
`close_requests_` are correctly `mpsc_queue` (thread-safe), but the actual map mutation
they trigger is not. Reachable via the debug tree inspector's Ctrl+Shift+I hotkey (opens/
closes a secondary window) or any app using `request_window()`/`close_window()` — a real,
tested, dogfooded feature. `submit()` calls happening on the logic thread during that
window race the main thread's `emplace`/`erase`. Not covered by the TSan CI job in any
obvious way (timing-dependent, needs a window open/close racing a publish).

**3. `transaction.hpp` cycle-guard leaves stale closures in thread-local state on overflow.**
`include/prism/core/transaction.hpp:58-84` (`TransactionGuard::flush`). On the 64th wave
(a non-converging cascade, e.g. two `Derived<T>`/`Field<T>` that recompute each other),
the loop does `assert(false && "...")` then `break` — but `assert` compiles to nothing
under `NDEBUG` (release builds, meson's `b_ndebug=if-release`), so only the `break` runs.
`tx.queue` (the `thread_local TransactionState`, `transaction.hpp:20-23`) is **not
cleared** at that point — it still holds `DeferredEmit` closures from the aborted wave.
Because `TransactionState` is `thread_local` and persists for the thread's lifetime, the
**next**, unrelated `prism::transaction(...)` call on that same thread will append to
this already-nonempty queue and then flush it — replaying the stale closures. Those
closures capture `this` pointers into whatever objects triggered the original cycle; if
those objects have since been destroyed (e.g. they were locals that went out of scope),
this is a use-after-free triggered by code that has nothing to do with the original bug.
`tests/test_transaction_cycle_guard.cpp` only asserts the loop *terminates*
(`a.get() > 0`), not that `tx.queue` is left clean afterward — this gap is untested.
Fix: `tx.queue.clear()` (and reset `tx.depth = 0`) before/on the overflow `break`.

**4. Python: startup race between `_is_running()` and the real dispatch handle.**
`python/src/prism_ext.cpp:1104-1138` (`run`/`_run_headless`) flips `g_has_handle` true
synchronously before `model_app(...)` is even called; `g_post_handle` is only populated
later, inside `setup(ctx)` on the logic thread, itself after `backend.wait_ready()`
(`model_app.hpp:269-311`). `try_post_via_handle_impl` (`:51-70`) and `dispatch_sync_read`
(`:109-118`) both treat "handle true, post_handle unset" the same as "no app," and fall
through to a **direct unsynchronized** `Field<T>::set()`/`get()`
(`include/prism/core/field.hpp:18-25` — plain unlocked `value = std::move(new_value)`).
A background Python thread polling `prism._is_running()` (the test suite does exactly
this pattern) can start writing fields from its own thread while the logic thread is
still inside `wait_ready()`. Structurally invisible to the current test suite because it
only exercises the headless backend (`wait_ready()` is a no-op there); real for
`prism.run()`'s `SoftwareBackend`, whose `wait_ready()` does real window-manager work.
Narrower residual of the race commit `8d085fc` already fixed for steady state.

**5. Font path baked in as a build-machine absolute path — silently breaks on any installed wheel.**
`src/meson.build:30,37` computes `font_path` from `meson.project_source_root()` and bakes
it into the binary via `-DPRISM_FONT_PATH`. `src/backends/software_backend.cpp:14-21,
100-102` uses it as the fallback and calls `TTF_OpenFont` with no error handling — `font_`
just stays null if missing. The font file is never installed/packaged
(`python/prism/meson.build` only installs `_prism_ext` and `__init__.py`). Any wheel
built on one machine and installed on another loses all default text rendering, silently.

## MEDIUM

**6. Undocumented, untested lifetime contract in `SenderHub::connect()`.**
`include/prism/core/connection.hpp:72-74`'s `detach` closure captures a raw `this`
(the `SenderHub`, i.e. whatever `Field<T>`/`Derived<T>`/`Shared<T>` owns it). Any
cross-object subscription — e.g. `Derived<T>::subscribe()` (`derived.hpp:44-49`) storing
a `Connection` into its own `connections_` from a *source's* hub — requires the source to
outlive the observer, or the observer to disconnect first. Nothing enforces or documents
this ("source must outlive derived"); `doc/design/reactivity.md` and
`doc/design/threading-model.md` don't mention it; `tests/test_derived.cpp` has no case
for "source destroyed before derived." Same-object subscriptions (the common case:
`observers_` connecting to the object's own `changed_`) are safe because member
destruction order (reverse declaration order) tears down `observers_` before `changed_`.
Cross-object composition is the risky, undocumented case.

**7. Python: `derived()` dependency lifetime only defended for `Bound*` handles.**
`prism_ext.cpp:530-585` (`derived_attach_dep`) only registers into `dep_owners_` when
`requires { h.owner; }` — true for `Bound*` handles, false for standalone
`FieldHandle<T>`/`SharedHandle<T>`. Not reachable through the documented `derived()`
Python API today (every path happens to closure-capture the dependency some other way),
but a latent trap if a future code path stops doing so accidentally.

**8. `subprojects/stdexec.wrap` pins `revision = main` — builds not reproducible.**
It's `[wrap-git]`, not `[wrap-file]`; `revision = main` is a moving branch, not a commit.
`meson wrap update` (wrapdb-only) silently skips it, and there's no pinned commit for
`meson subprojects update` to fall back to either — two builds a week apart can pull
different stdexec code with no record of which. `magic_enum.wrap` does this correctly
(pins tag `v0.9.7`).

**9. Docs undersell the Python bindings' actual status.**
`README.md:518` lists Python bindings under future/Phase 5; `doc/design/README.md:78`
and `doc/design/python-sdk.md:1-3` both say `Status: Design`. Actual state: 1162+587
lines of working, tested code, wired into `meson test`, the last 5 commits on `main`.
Undersell, not oversell — nothing silently broken, but misleading for status tracking.

**10. `doc/design/render-backend.md` and `scene-snapshot.md` are stale against current headers.**
`render-backend.md:12-20`'s `BackendBase` snippet shows the pre-multi-window,
single-`submit(snapshot)` interface; actual `include/prism/app/backend.hpp:15-27` has

`scene-snapshot.md:10-15` is missing over half of `include/prism/render/scene_snapshot.hpp`

mention.
