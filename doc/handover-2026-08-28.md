## What shipped, and why it matters

### 1. Snapshot instrumentation (`ea3f363`)
`SceneSnapshot` gained `build_time_ms`, `dirty_widget_count`, `draw_command_count`,
`approx_bytes`, `layout_pass_count`, populated in `WidgetTree::build_snapshot()`. Live in the
debug tree inspector (`Ctrl+Shift+I`, requires `prism_debug_tools`) as a one-line summary above
the tree/detail split. This is the "instrument before optimizing" step the review asked for, and
every fix after it in this list was found or verified using these numbers.

### 2. Per-widget DrawList sharing (`f162585`)
The biggest structural change. `SceneSnapshot::draw_lists` was `vector<DrawList>` (copied by
value every publish, for every visible widget, regardless of dirty state — a real, present-tense
cost, not the future risk the external report framed it as). Changed to
`vector<shared_ptr<const DrawList>>`; `WidgetNode` now caches the last translated+clipped
`DrawList` plus the screen rect it was computed for, and `layout_flatten()` reuses it when the
widget is neither dirty nor relocated since last frame.

**Scoped deliberately**: only applies to widgets with no clipping ancestor (not inside
Scroll/VirtualList/Table) — `resolve_clips()` mutates a `ClipPush` rect in place only when an
outer clip is already active, which by construction only happens for entries built fresh that
call, so sharing outside that case is provably safe. **Rows inside scrolling/tabular containers
still rebuild every frame** — this is a named, deliberate gap (`simplify:` in the code), not an
oversight. If a future profiling session shows scrolled/tabular content dominating
snapshot-build cost (the "100k-row table" showcase workload, as opposed to the "1M-point plot"
one this fix already covers), that's where to look next.

Touched 18 files — 11 of them were mechanical test-file fixes for the type change
(`dl.commands` → `dl->commands`, `push_back(std::move(dl))` →
`push_back(std::make_shared<DrawList>(std::move(dl)))`). If you're auditing this commit, the
substance is in `include/prism/ui/layout.hpp` (the cache-check itself) and
`include/prism/render/scene_snapshot.hpp` (`resolve_clips`'s `const_pointer_cast`, which has a
comment explaining exactly why it's safe).

### 3. `z_order` width (`bbef5e4`)
Trivial: `uint16_t` → `uint32_t`. Was silently wrapping past 65535 draw-list entries — flagged as
trivial-but-real in the review. Reproducer built a 70k-leaf `Row` and confirmed the wrap
(`69999` came back as `4463`) before fixing it.

### 4. Double layout pass (`809654c`)
`build_snapshot()` was unconditionally redoing a full second materialize+layout pass whenever
`check_dirty(root_)` was true after the first pass. Turned out that's true on *every* publish for
any app using a `VirtualList`/`Table` (they always freshly rebind their visible rows, which marks
those rows dirty regardless of whether the viewport moved) — not just "the first frame," as the
old comment claimed. Replaced the gate with a direct before/after comparison of each
`VirtualList`/`Table`'s own resolved viewport height across the first pass.

### 5. Stall-latency benchmark (`f7f9524`) — surfaced the biggest finding
New `benchmarks/` directory (own meson subdir, `ninja benchmarks/bench_stall_latency`, run
directly — not a doctest case). Uses the same threaded backend/app-thread split `model_app()`
uses in production, headless, to measure how long an input event takes to reach the screen when
the app thread's own `record()` is slow (simulates a plot recomputing a large series). Confirms
in numbers what reading `software_backend.cpp` already implied: there's no independent render
cadence, so input latency is bounded below by app-thread busy time.

Building it surfaced an unplanned, bigger bug: latency tracked the stall **2:1**, not 1:1. Traced
to `update_canvas_bounds()` unconditionally re-running a dirty widget's `record()` a second time
post-layout. Fixed in the next commit.

### 6. Double `record()` call fix (`91d7c29`)
`update_canvas_bounds()` re-records every `Leaf`/`Canvas`/`Handle` widget in a window on every
publish, unconditionally — the *point* is to let delegates draw at their final allocated size
(known only after layout) instead of the pre-layout guess `refresh_dirty()`'s earlier pass used.
But it had no check for whether the size actually *changed*, so every dirty widget paid for
`record()` twice, and — worse — **every untouched sibling in the same window also paid for one
full `record()` call, purely because something else made the window dirty.** A dashboard with 50
fields, one edited, meant 50 `record()` calls where 1 was needed.

Fixed by gating the re-record on `wn->canvas_bounds.extent != layout_node.allocated.extent`.
Safety argument (audited every `Widget<T>` specialization in the repo, including the one
genuinely content-dependent case, `TextArea`, whose height depends on row count — still correct,
because a `rows` change flows through the measure pass and does change the allocated extent):
see the comment on `update_canvas_bounds()` in `widget_tree.hpp` and
`tests/test_record_reuse.cpp`. Benchmark result: `bench_stall_latency`'s
`untouched_sibling_record_calls` dropped 1→0, `trigger_record_calls` dropped 2→1, and latency
overhead over the raw stall dropped from ~1x the stall (2x total) to sub-millisecond jitter. The
benchmark now asserts these counts itself, so a regression here will make it fail loudly.

### 7. Golden snapshot tests (`c2b6017`)
`TestBackend` already replayed scripted `InputEvent` sequences headlessly, but its `submit()`
discarded every result. Gave it a `submitted()` accessor. New `tests/test_golden_snapshot.cpp`
serializes a `SceneSnapshot`'s rendered content deterministically (geometry + draw commands in
z_order + overlay) and diffs it against a frozen string, for two cases: initial publish, and
after a scripted checkbox click. Sanity-checked it has real teeth by temporarily shifting a
checkmark glyph 1px and confirming a precise diff, then reverting. This is the harness the review
called "one week of work" — turned out to be one accessor plus one test file.

## What's left (from `doc/review-2026-08-28.md`'s order)

- **Step 4 — `WidgetTree` decomposition.** `widget_tree.hpp` is 1960+ LOC mixing a builder DSL,
  focus/drag state machines, virtualization, and the frame pipeline. Not started. This is a
  genuine refactor (behavior-preserving structural split), bigger and more invasive than anything
  in this session — budget a dedicated session for it, probably with `superpowers:writing-plans`
  first given the size.
- **Step 5 — `Channel<T>` for ordered events.** Needs a forcing function — an event-stream/log
  panel added to `model_system_monitor` — not attempted yet.
- **DrawList-sharing follow-up** (noted above): extend the caching to Scroll/VirtualList/Table
  rows, if profiling ever shows that's where the cost actually is. Not scheduled; no evidence yet
  that it's needed.
