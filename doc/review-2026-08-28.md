# PRISM — Independent Review Response

**Date:** 2026-08-28
**Context:** Response to `PRSIM_review_report.md` (2026-08-26), verified against the actual codebase
(`include/prism/`, `src/`, `examples/`, `tests/`) and recent development history.

---

## Where the report is right — and where it's actually *understating* things

**The snapshot pipeline is heavier than the report says.** The report flags "full publication
implies substantial copying" (§4.2) as a future risk. It's already the present cost model: every
publish does `make_unique<SceneSnapshot>()` (`include/prism/app/widget_tree.hpp:1012`), **copies
every widget's DrawList into a LayoutNode** (`widget_tree.hpp:1884`), then moves each into *another*
fresh DrawList wrapped in clip push/pop (`include/prism/ui/layout.hpp:459-468`). Dirty tracking only
gates `record()` re-runs — it does nothing for layout or snapshot assembly. And `build_snapshot` can
run layout **twice** per frame because virtual lists need viewport sizes from the first pass
(`widget_tree.hpp:1002-1008`). So the report's "prototype chunked sharing" recommendation is
correct, but there's a cheaper first move it doesn't name: make the snapshot hold
`shared_ptr<const DrawList>` per widget and share unchanged widget draw lists across snapshots.
That's structural sharing without inventing a chunk abstraction.

**The threading claim is weaker than both the README and the report assume.** The report says the
renderer "can keep rendering the previous snapshot" during app stalls. In code, the backend thread
renders once per SDL event batch, and the wake event is *enqueued by the app thread after publish*
(`src/backends/software_backend.cpp:287-315`). There is no vsync, no frame pacing, no independent
render cadence. If the app thread stalls, nothing presents — the last frame just stays on screen
(which is visually fine, but it's "no redraw," not "independent rendering"). Also blurred boundary:
the app thread holds its own shared_ptr to the published snapshot and hit-tests against it for input
routing (`include/prism/app/window_registry.hpp:18`, `include/prism/app/model_app.hpp:169-175`).
That's pragmatic and probably necessary, but the README's one-way-handoff diagram isn't what the
code does.

**"C++26 senders for observers" is marketing.** `SenderHub` is a `std::vector<std::function>` with
manual RAII connections (`include/prism/core/connection.hpp:42-84`). stdexec only schedules the app
loop. The report takes the README's sender/receiver framing a bit too much at face value. Not a
problem per se — the vector-of-functions design is honest and adequate — but the README should stop
implying otherwise.

**Zero performance infrastructure exists.** This is the strongest point of agreement with the report
(its Priority A), and it's worse than the report knew: no FPS counter, no frame-time stats, no
snapshot statistics, no Tracy, no benchmark tests — nothing. The only quantitative artifact in the
entire repo is one perf-motivated bugfix (mouse-motion coalescing, `33feacd`), which is itself
evidence that full-rebuild-per-event already caused visible cursor lag. For a project whose README
thesis is "frames must be guaranteed independent of business logic," having no numbers at all is the
biggest gap between claim and proof.

## Things the report missed

- **`z_order` is `uint16_t`** (`include/prism/render/scene_snapshot.hpp:19`) — a silent 65k
  draw-list ceiling. Trivial fix, but it will bite exactly the large-scene workloads the project
  wants to attract.
- **The raw-pointer `index_` invariant is more fragile than its own comment admits**
  (`widget_tree.hpp:31-32`): safety rests on "tree never mutates after build," yet tabs and virtual
  lists *do* mutate lazily, compensated by `unindex_subtree` bookkeeping. That's a latent bug class,
  not just a code-smell.
- **Deterministic input replay already half-exists.** The report recommends it as new testing work
  (§11.2), but `TestBackend` already replays scripted `InputEvent` vectors headlessly, and
  `CapturingBackend` captures submitted snapshots for structural assertions. Golden snapshot tests
  are therefore *cheap* — the harness is built, only the goldens are missing. This should be
  promoted from "strategy to add" to "one week of work."
- **The examples' data sources are already tested headlessly** (`proc_metrics`, `file_tree_source`
  have their own test files). Good pattern — system-monitor-driven development already flushed out
  real framework bugs (drain-on-tick, AnimationClock livelock). The report's
  "reference-app-driven validation" instinct is already the project's de facto discipline.

## Where I disagree or would re-rank

- **Semantic metadata → serialization/CLI (report's Priority B / Phase 2)** is attractive but it's
  scope expansion into a config-framework direction. For an R&D project whose identity question is
  still "is the scene architecture good enough," measurement (Phase 1) and the scene compiler
  (Phase 3) should stay strictly ahead, with serialization pulled in only as *demo fuel*
  (load/save in one showcase), not as a framework layer. The report's own verdict ("don't become a
  Qt competitor") argues against spending phase 2 on metadata generalization too early.
- **The instrument-console showcase (report's #1) mostly exists.** `model_system_monitor` already
  proves cross-thread `Shared<T>`, live stacked plots, sortable table, lazy tree — and recent
  history shows it and the plot widget co-evolving. Building a separate instrument demo would
  duplicate the reference app. Better: keep evolving system_monitor (add an event stream panel →
  motivates the `Channel<T>` abstraction naturally) or reskin the same architecture as a mock
  instrument with simulated telemetry.
- **Frame pacing** is missing from the report as a work item. The render path is event-rate-bound,
  so "60 FPS" currently means "however fast SDL delivers events." A vsync'd or timer-driven present
  cadence is a small change that makes all future FPS numbers meaningful.

## Recommended order of work

1. **Instrument before optimizing**: snapshot stats (build time, bytes, dirty count, version)
   exposed through the existing debug-tools hotkey path (the `prism_debug_tools` option already
   gates the inspector — same mechanism). Then the stall benchmark the report asks for: block the
   app thread 10–500 ms, measure present latency and input lag. With numbers, the copy-per-frame
   question answers itself.
2. **Cheap structural wins**: per-widget `shared_ptr<const DrawList>` sharing in the snapshot; kill
   the double layout pass; `uint32_t` z_order. All small, all measurable with step 1.
3. **Golden snapshot tests** on top of the existing Capturing/Test backends — deterministic
   regression for the whole event→scene path, at a fraction of the report's estimated cost.
4. **WidgetTree decomposition** — agree with the report's §5.1 fully. 1960 LOC mixing a 630-line
   builder DSL, focus/drag state machines, virtualization, and the frame pipeline. Splitting out
   virtualization and the snapshot builder is also the prerequisite for an explicit scene compiler
   (report's D2), so it pays twice.
5. **`Channel<T>` for ordered events** — agree, and the system monitor's log panel is the natural
   forcing function.

---

## Best demos to build (ranked)

1. **The perf lab as a visible demo** — one app with a 100k-row table, a 1M-point plot, a synthetic
   1 kHz telemetry source, and an on-screen overlay showing snapshot age/build time/FPS. This single
   artifact is simultaneously the report's A1, A2, and Showcase #3, and it produces the README
   numbers the project lacks. Highest value by far.
2. **"A GUI from a struct" in 30 seconds** — cheapest to make, highest communication value. It
   nearly exists already across `model_dashboard`/`showcase`; polish one into the canonical README
   demo. If validation/serialization lands even in demo form,
   `load(settings, "config.toml")` + generated UI is the viral version.
3. **PRISM inspecting PRISM** — the tree inspector exists; wire the snapshot stats from step 1 into
   it. Communicates the architecture better than any diagram, and it's mostly plumbing, not new
   subsystems.
4. **Transaction-driven undo/redo demo** — small, and it's the one demo that makes the transaction
   machinery legible to an outsider.
5. **Skip for now**: a separate instrument console (covered by system_monitor) and the universal
   object inspector (nice, but it sells reflection, which is already the best-documented strength).

---

## Bottom line

The report's core thesis stands — prove the architecture before growing the widget catalog — but the
code shows the scene-production cost is already a present-tense problem, not a future risk, and the
measurement infrastructure it asks for is a smaller build than the report implies because the
headless test backends are already in place.
