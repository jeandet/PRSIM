## Open — MEDIUM

**1. `PlotHandle`/`TreeHandle`/`BoundTree` bypass the thread-dispatch machinery.** (new,
from `5642cb2`)
`python/src/prism_ext.cpp:303-327` (`PlotHandle::add_series/clear_series/notify/reset_view`),
`:412-432` (`BoundTree::refresh/rows`), `:433-449` + `:1195-1210` (`TreeHandle`).
Every other handle type (`FieldHandle`, `SharedHandle`, `BoundPlot`'s own `add_series`)
routes through `field_set_dispatch`/`list_op_dispatch`/`dispatch_sync_read`
(`prism_ext.cpp:115-135`, `:221-235`), which detect off-logic-thread calls and post across.
These three skip it and call straight into `PlotModel`/`TreeController`, which hold a
plain unsynchronized `std::vector` (`PlotModel::series_`, `include/prism/widgets/plot.hpp:314`).
Calling any of them from a non-logic thread races the render/logic thread. Currently
unreachable — no example/test calls these off-thread, and `PlotHandle`/`TreeHandle` have
zero test coverage despite being in `__all__`.
Fix: mirror `BoundPlot::add_series`'s dispatch pattern (`prism_ext.cpp:684-705`) in the
other three; add a background-thread test.

**2.** Early off-thread `post`/`set` calls that land inside the 200ms startup spin window
(added by `18354ed`'s HIGH-6 fix), if that window is ever exceeded (slow debug build,
loaded CI runner), fall through to `PostResult::NoApp` and are silently dropped — not
queued, not retried, no exception raised. `prism_ext.cpp:56-65`.

**3.** `dispatch_sync_read`'s "closed ⇒ safe to read directly" assumption is narrow: once
`closed_flag` is observed true, reads go unsynchronized, but other already-queued drain
continuations on the scheduler can still run afterward and touch the same
zero-internal-synchronization `Field<T>`. `prism_ext.cpp:122-124`. Shutdown-only window.

**4.** `create_window()` (direct, unsynchronized) and `request_window()` (thread-safe,
queued) coexist on the same public `Backend` API with nothing stopping `create_window()`
from being called after `run()` starts on another thread. `software_backend.hpp:35`,
`.cpp:47-55` vs `:57-66`. Correct today only by caller convention, not enforcement.

**5.** `include/prism/app/widget_tree.hpp` decomposition is only partial: still 1198
lines, with `widget_tree_layout.hpp` (168 lines) and `widget_tree_traversal.hpp` (81
lines) extracted alongside it. `doc/design/README.md`'s table has no entry for
`widget_tree.hpp` at all, so there's no canonical doc reflecting the actual current state.

## Open — LOW

**6.** `windows_mutex_` doesn't cover `windows_.find(wid)` reads inside `run()`'s SDL
event switch (`software_backend.cpp:196,204,231,271,289`). Same-thread-only today, not a
live race, but contradicts the "all...paths locked" framing and would break if window
creation ever moved to a second thread.

**7.** `Derived<T>`'s "hub must outlive connection" contract (`derived.hpp:44-49`,
`connection.hpp:65-68`) is documented but not compiler-enforced. Informational, tied to
the `SenderHub` move-safety tradeoff `18354ed` deliberately accepted rather than fixed.

**8.** `subprojects/magic_enum.wrap` pins a tag (`v0.9.7`), not a commit hash, unlike
`stdexec.wrap`'s SHA pin. Low practical risk, inconsistent rigor.

**9.** No dedicated concurrent-access test for `windows_mutex_`
(`tests/test_software_backend_request_window.cpp` is single-threaded;
`tests/test_software_backend_chrome_cursor.cpp` drives a second thread but only exercises
cursor/chrome state). Nothing would catch the mutex being removed or a new unlocked
access site added.

**10.** Test coverage gaps: no `List<bool>` int-coercion disablement-path test, no
multithread torture test crossing GC + `observe()` simultaneously, and zero `derived()`
coverage at all (the BLOCKER-1 fix landed with no regression test for the bug it fixed).
